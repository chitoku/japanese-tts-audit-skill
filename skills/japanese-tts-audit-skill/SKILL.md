# Japanese narration pronunciation audit

Accept the user's script and existing audio. Produce an HTML/JSON report that lets them listen to suspected reading differences. The CLI does the processing; the agent explains what requires confirmation.

For authorized repairs, retain the creator’s existing TTS service, model, voice and relevant settings when available. Use session context or source-project metadata first; ask only for missing settings needed to reproduce the voice. Use the available provider API, CLI, connector or editable source project. Do not switch to ElevenLabs merely because this repository has an ElevenLabs generator. If the existing service cannot be operated, provide the affected sentence and generation-only reading changes for the creator to regenerate, then inspect the returned audio. A service that exposes neither audio nor editable segments may require an export or a manual step.

For sentence-by-sentence generation, repair and assembly supported by the CLI, use [references/sentences.md](references/sentences.md). Generation may consume provider credits; local engines such as VOICEVOX can run without paid API usage. Inspection of existing audio remains local. A proofreading request alone does not authorize paid generation.

## Run

1. Locate the audio and UTF-8 script. Preserve them. Use an interpreter with `tts_audit` installed; see the repository README for installation. The recognition extra downloads about 3.24 GB on first use. Reuse an existing cache when available. This is local inference, not an API service.
2. Run `python -m tts_audit.cli check AUDIO --script SCRIPT --out NEW_DIRECTORY`. Optional flags: `--readings readings.json` for user-specified readings, `--cache-dir CACHE`, and `--offline` after the model is cached. The equivalent command is `tts-audit check ...`. Use absolute input/output paths if running outside the input directory. `scripts/check.py` is also an entry point using the current interpreter.
3. Local recognition obtains audio-derived token timestamps in the same decode by default and saves `audio-timing.json` plus `timeline.html`. This uses cross-attention/DTW; multi-kana tokens and unmatched text need interpolation, so positions are estimates, not certified word boundaries. `--no-timestamps` skips this extra local compute. If timing fails, inspection continues with approximate segment-based positions; disclose `audio_timing` in the CLI summary. Transcript imports do not start local recognition for timing.
4. The default converts the script to expected kana with Sudachi, independently transcribes audio with the pinned Kana Whisper model, and compares them. Never insert the script, desired reading, listening labels, or suspected wrong word into ASR recognition. A user's explicit pronunciation overrides belong only on the script side.
5. Boundary-adjacent differences trigger one automatic shifted-segmentation pass. Check `boundary_recheck.status`: if failed or inconclusive, retain the original candidates. The report lowers priority only when the expected reading plus surrounding context matches in the second pass. Original hypotheses and playable cards stay under the boundary section. This is not a correct verdict. ASR is audio-only in both passes.
6. Prefer `tts-audit serve REPORT_DIRECTORY` (or `python -m tts_audit.cli serve REPORT_DIRECTORY`) and open/link the returned `timeline_url` (the waveform review page) while keeping the process alive. Audio-timed pages start with playback-follow enabled unless the user has saved another preference. The CLI serves the shared listening UI and writes human decisions directly to `review-state.json`. Use [references/review-server.md](references/review-server.md) for the state contract and recovery. If a local server cannot run, open/link `report.html` and use exported notes JSON. Describe candidate count as reading differences needing review, not a count of proven TTS errors. Surface low text/audio alignment, unknown dictionary readings, and any secondary-pass differences. Show the audio with the report so the user can check. If no actionable candidate remains, preserve the original audio; a check-only outcome is a successful workflow and needs no paid regeneration.
7. Distinguish audio-derived estimated positions from segment-based fallback positions. In server mode read `review-state.json`, match its run ID and report hash, ignore manual notes marked `deleted: true` as repair targets, and distinguish `draft` from `completed`. The completion button does not certify correct pronunciation or resolve uncertain/unreviewed cases. Browser completion does not itself launch a new Agent turn: the active agent can read/poll the state using its available execution tools. Do not request a JSON download/attachment in server mode. In file-only mode notes remain in browser storage and need JSON export/import.

## Interpret

- Distinguish TTS errors, dictionary/G2P mistakes, ASR mistakes, valid alternate readings, and ambiguous sound. "No difference" does not guarantee correct pronunciation.
- Standard-Japanese ヅ／ズ and ヂ／ジ spelling differences are normalized for audio comparison. A small surface-specific list of alternate readings (払拭, 施工, 私, いう) remains in JSON and playable cards at `low_variant` priority when the expectation came from the dictionary. An explicit `--readings` difference retains normal priority even if it matches that list. Do not treat a lower-priority card as human-confirmed correct or learn global pronunciation exceptions from a single listening label.
- Look beyond any original benchmark target: a correct target does not imply the whole sentence is correct.
- Record observed sound separately from claims about its cause. Cross-language-like sounds or dictionary-inexplicable readings do not prove a mechanism.
- This preview uses whole-script sequence alignment and audio segments split near low-energy boundaries. Numeric readings, names, accepted variants, chunk boundaries, and major script/audio differences need care. Use `--readings` for known vocabulary; do not silently rewrite the script or regenerate audio.
- `--readings` changes the detector's expectation, not the TTS audio. If a genuine audio error needs repair within an authorized generation task, keep the canonical script, change only the generation input (e.g. 掘削→くっさく or a supported pronunciation alias), and recheck the entire regenerated audio against the canonical script. Do not retry generation just to satisfy an unstable ASR hypothesis; listen first, keep a budget/attempt limit, and allow rollback.
- For an authorized narration repair, regenerate only the affected sentence using the existing provider and preserve approved audio. Use provider-neutral `sentences init` (default external mode), then the existing service’s API/CLI/editor to generate or regenerate the affected sentence. Import the returned audio with `sentences import-audio`, including the actual generation input via `--text-file` after reading changes, and service/model/voice/settings via `--source-json` when known. Recheck the candidate and approve it before selecting it; retain the prior selected version and other approved sentence assets. The built-in ElevenLabs generator is an optional adapter only for a matching existing workflow, not the default repair route. Keep canonical text, generation text, audio hashes and review basis together. Inspect joins for pauses, volume and delivery. Existing continuous audio can still be inspected with `check`; sentence generation does not require splitting every incoming recording.
- If recognition fails, report failure rather than interpreting partial audio as a clean pass. The output directory must be new so prior notes/media are preserved.

For transcript import, output fields, privacy and the concrete limitations, read [references/io.md](references/io.md). No telemetry is sent and no leaderboard is maintained by this tool.
